# Первичная настройка Linux-сервера (VPS)

Учебный материал и автоматизация первичной настройки сервера на Ubuntu/Debian:
от создания пользователя и защиты SSH до удобной командной строки и Docker.

Каждый раздел устроен одинаково:

1. **Зачем** — какую проблему решает шаг.
2. **Вручную** — команды, которыми это делается руками (чтобы понимать, что происходит).
3. **Что делает скрипт** — какой модуль за это отвечает и какие настройки его меняют.
4. **Проверка** — как убедиться, что всё работает.
5. **Частые ошибки** — на чём обычно спотыкаются.

В конце — шпаргалка по ежедневным командам.

## 0. Как пользоваться скриптом

Поддерживаются **Ubuntu 22.04+ и Debian 12+**, архитектуры **x86_64 и ARM64 (aarch64)**.

### Перед созданием сервера

При заказе VPS в панели хостинга (cloud.ru, timeweb, DigitalOcean) добавьте свой
**публичный SSH-ключ**. Если ключа ещё нет, создайте его на своём компьютере:

```bash
ssh-keygen -t ed25519 -C "aleksey@laptop"   # создаст ~/.ssh/id_ed25519 и id_ed25519.pub
cat ~/.ssh/id_ed25519.pub                   # это содержимое вставляется в панель хостинга
```

Приватный ключ (`id_ed25519`, без `.pub`) никогда никуда не копируйте.

### Запуск

```bash
# 1. Зайти на свежий сервер под root
ssh root@<IP>

# 2. Получить скрипт (git есть не на всех образах — поставим)
apt-get update && apt-get install -y git
git clone <url-репозитория> vps_init && cd vps_init
#    или скопировать со своей машины:  scp -r vps_init root@<IP>:~

# 3. Настроить конфиг
cp vps_init.conf.example vps_init.conf
nano vps_init.conf            # как минимум USERNAME

# 4. Запустить
./vps_init.sh
```

**Не закрывайте сессию root**, пока не проверите в *новом* окне терминала, что
можете войти под своим пользователем: `ssh aleksey@<IP>` и выполнить `sudo -v`.

### Параметры

```text
./vps_init.sh --help                 справка
./vps_init.sh --list                 список модулей
./vps_init.sh -c my.conf             другой файл конфига
./vps_init.sh -u aleksey             имя пользователя без правки конфига
./vps_init.sh -p desktop             профиль для локальной машины (без ssh и firewall)
./vps_init.sh --only tools,docker    выполнить только эти модули
./vps_init.sh --skip docker          выполнить всё, кроме docker
```

Приоритет настроек: **флаги > `vps_init.conf` > значения по умолчанию** в `vps_init.sh`.

Скрипт можно **запускать повторно**: уже сделанное пропускается (`[SKIP]`).
Так удобно добавлять модули или менять конфиг на уже настроенном сервере.

## 1. Как устроен скрипт

```text
vps_init/
├── vps_init.sh            точка входа: флаги, конфиг, запуск модулей, итоговая сводка
├── vps_init.conf.example  все настройки с комментариями
├── lib/
│   ├── log.sh             логирование
│   └── utils.sh           общие функции: apt, бэкапы, определение ОС/архитектуры
├── modules/               по одному файлу на раздел этого материала
│   └── 00_preflight.sh …
└── dotfiles/              конфиги пользователя (.bashrc, .vimrc, .tmux.conf, .gitconfig)
```

### Строгий режим bash

В начале скрипта стоит:

```bash
set -Eeuo pipefail
```

| Опция | Что делает |
|---|---|
| `-e` | остановиться при первой команде, завершившейся с ошибкой |
| `-u` | ошибка при обращении к необъявленной переменной (ловит опечатки в именах) |
| `-o pipefail` | конвейер `a \| b` считается неудачным, если упала любая его часть, а не только последняя |
| `-E` | ловушка `trap ... ERR` срабатывает и внутри функций |

Без этого bash по умолчанию «молча» продолжает работу после ошибок, и скрипт может,
например, запретить вход root, не создав перед этим пользователя.

### Модули

Каждый файл в `modules/` — это один логический шаг. Он содержит описание и функцию `module_run`:

```bash
MODULE_DESC="Проверки: ОС, архитектура, сеть, диск, память"

module_run() {
  check_os
  check_arch
  ...
}
```

Главный скрипт выполняет модули по порядку имён (`00_`, `10_`, `20_` …), каждый —
**в отдельном подпроцессе** `( ... )`. Поэтому:

- ошибка в одном модуле прерывает только его, остальные продолжают работу;
- функции и переменные разных модулей не мешают друг другу;
- фатальная ошибка (`fatal "..."`, код выхода 99) останавливает весь запуск —
  так делает, например, `00_preflight` на неподдерживаемой ОС.

### Идемпотентность

Идемпотентная операция при повторном выполнении даёт тот же результат, что и при первом,
и ничего не ломает. Каждый шаг сначала проверяет, не сделан ли он уже:

```bash
# плохо: при повторном запуске строка добавится второй раз
echo "vm.swappiness=10" >> /etc/sysctl.conf

# хорошо: добавить, только если такой строки ещё нет (функция ensure_line в lib/utils.sh)
grep -qxF "vm.swappiness=10" /etc/sysctl.conf || echo "vm.swappiness=10" >> /etc/sysctl.conf
```

Перед изменением любого системного конфига скрипт сохраняет копию рядом с ним:
`/etc/ssh/sshd_config.bak.2026-10-20_211500`. Откатиться можно простым копированием.

### Логирование

В консоли — короткий статус каждого шага:

```text
==> 00_preflight — Проверки: ОС, архитектура, сеть, диск, память
  [ OK ] ОС: Ubuntu 24.04.4 LTS
  [ OK ] Архитектура: x86_64
  [SKIP] Уже установлено: curl ca-certificates
  [WARN] Мало RAM и нет swap — рекомендуется ENABLE_SWAP=true в конфиге
  [FAIL] Установка: docker-ce (код 100, подробности в /var/log/vps_init/...)
```

В лог-файле `/var/log/vps_init/vps_init-<дата-время>.log` — всё подробно, включая полный
вывод каждой команды (например, `apt-get`). Последний лог всегда доступен по ссылке
`/var/log/vps_init/latest.log`:

```bash
less /var/log/vps_init/latest.log          # прочитать
grep -E 'FAIL|WARN' /var/log/vps_init/latest.log   # только проблемы
```

Права на каталог логов — `700`, на файл — `600` (читает только root): в логах может быть
информация о системе, которую не стоит показывать другим пользователям.
**Пароли в лог не пишутся никогда** — поэтому их не передают аргументами команд.

В конце работы печатается итоговая сводка: сколько шагов выполнено, пропущено,
с предупреждениями и ошибками, список проблем и блок «Что дальше»
(например, команда для подключения под новым пользователем).

### Прочие защиты

- **Блокировка запуска** (`flock`): два экземпляра скрипта одновременно не запустятся.
- **Ожидание apt**: на свежем VPS сразу после загрузки часто работает автообновление
  и держит блокировку dpkg. Вместо ошибки `Could not get lock /var/lib/dpkg/lock-frontend`
  скрипт ждёт до 5 минут (`apt-get -o DPkg::Lock::Timeout=300`).

## 2. Проверки перед запуском

**Модуль:** `00_preflight`. Ничего не меняет в системе, только проверяет.

| Проверка | Если не прошла |
|---|---|
| ОС — Ubuntu или Debian | остановка всего запуска |
| Архитектура — x86_64 или aarch64 | остановка |
| DNS и доступ в интернет (github.com:443) | остановка |
| Свободно на `/` не меньше 2 ГБ | предупреждение |
| Мало RAM (< 2 ГБ) и нет swap | предупреждение с советом включить `ENABLE_SWAP` |

### Вручную

```bash
cat /etc/os-release          # дистрибутив и версия
uname -m                     # архитектура: x86_64 или aarch64
getent hosts github.com      # работает ли DNS
df -h /                      # место на диске
free -h                      # память и swap
```

Интересная деталь: сеть проверяется без `curl` (на минимальных образах его может не быть)
— через встроенную в bash псевдо-файловую систему `/dev/tcp`:

```bash
timeout 5 bash -c 'exec 3<>/dev/tcp/github.com/443' && echo "есть доступ"
```

А память читается из `/proc/meminfo`, а не из `free`: вывод `free` зависит от языка системы
(`Mem:` в английской локали и `Пам:` в русской), и парсить его ненадёжно.

## 3. Система: обновления, время, hostname, swap

**Модуль:** `10_system`. **Настройки:** `APT_UPGRADE`, `TIMEZONE`, `NEW_HOSTNAME`,
`ENABLE_SWAP`, `SWAP_SIZE`, `ENABLE_AUTO_UPGRADES`.

### 3.1. Базовые пакеты и обновление

**Зачем.** Образ VPS собирают заранее, и к моменту заказа сервера в нём уже есть
устаревшие пакеты, иногда с известными уязвимостями. Первое, что делают на новом
сервере, — обновляют систему. Заодно ставят пакеты, без которых не обойдутся
следующие шаги: `curl`/`wget` (скачивание), `ca-certificates` (проверка HTTPS),
`gnupg` (ключи репозиториев, например Docker), `unzip`, `sudo` (на минимальном Debian его может не быть).

**Вручную:**

```bash
apt update                       # обновить СПИСКИ пакетов (что есть в репозиториях)
apt list --upgradable            # что можно обновить
apt upgrade                      # обновить сами пакеты
apt install curl wget ca-certificates gnupg unzip sudo
```

`apt update` ничего не устанавливает — только скачивает свежий каталог.
Без него `apt install` может пытаться скачать версию, которой на сервере уже нет (ошибка 404).

**Что делает скрипт:**

- `apt update` — не чаще раза в час (повторный запуск скрипта не качает каталог заново);
- ставит только недостающие пакеты;
- сначала делает пробный прогон `apt-get -s upgrade` (`-s` — simulate, ничего не меняет)
  и считает, сколько пакетов обновится; если ноль — шаг пропускается;
- обновляет командой `apt-get upgrade --with-new-pkgs`: она может поставить новые
  зависимости (например, новое ядро), но **никогда не удаляет** установленные пакеты —
  в отличие от `apt full-upgrade`;
- если пакет хочет заменить конфиг, который уже меняли на сервере, оставляет старый
  (`--force-confold`), а новую версию кладёт рядом как `*.dpkg-dist` — без вопросов в терминале;
- на Ubuntu после обновления может всплыть синее окно *needrestart* «какие службы перезапустить?».
  Скрипт отвечает на него автоматически (`NEEDRESTART_MODE=a` — перезапустить всё нужное).

Если обновилось ядро, Ubuntu создаёт файл `/var/run/reboot-required`. Скрипт
не перезагружает сервер сам, а пишет предупреждение и напоминание в «Что дальше».

### 3.2. Часовой пояс и синхронизация времени

**Зачем.** Время на сервере видно в логах, в расписаниях (`cron`, systemd-таймеры),
в именах бэкапов. По умолчанию на VPS стоит UTC — читать логи в UTC неудобно.
А **точное** время нужно для HTTPS-сертификатов, двухфакторных кодов и сравнения логов
разных машин: часы без синхронизации уходят на секунды-минуты в месяц.

NTP (Network Time Protocol) — протокол, по которому система сверяет часы с серверами точного
времени. В Ubuntu/Debian этим занимается служба `systemd-timesyncd`.

**Вручную:**

```bash
timedatectl                                 # текущее время, пояс, статус NTP
timedatectl list-timezones | grep Moscow    # найти нужный пояс
timedatectl set-timezone Europe/Moscow
timedatectl set-ntp true                    # включить синхронизацию
```

**Что делает скрипт:** выставляет `TIMEZONE` (если такого пояса нет — предупреждение, не ошибка),
ставит `systemd-timesyncd`, если его нет, и включает NTP. Если на сервере стоит другая служба
времени — `chrony`, — ничего не трогает.

### 3.3. Имя хоста (hostname)

**Зачем.** Имя хоста видно в приглашении командной строки (`aleksey@web1:~$`) и в логах.
Хостинг называет сервер как попало (`vm-4f2a1c`, `ubuntu-s-1vcpu-1gb-ams3-01`) —
если серверов несколько, легко выполнить команду не на том. Короткое понятное имя (`web1`,
`db`, `vpn-nl`) спасает от этого.

**Вручную:**

```bash
hostnamectl set-hostname web1
nano /etc/hosts                  # строка: 127.0.1.1 web1
```

Строка в `/etc/hosts` нужна, чтобы имя сервера резолвилось локально. Без неё `sudo`
пишет `unable to resolve host web1` и подтормаживает на каждой команде.

**Подвох облака — cloud-init.** На облачных VPS работает `cloud-init`: при каждой загрузке
он применяет настройки из панели хостинга, в том числе **возвращает старое имя хоста**
и перезаписывает `/etc/hosts`. Поэтому скрипт кладёт файл
`/etc/cloud/cloud.cfg.d/99-vps-init-hostname.cfg`:

```yaml
preserve_hostname: true      # не менять имя хоста
manage_etc_hosts: false      # не перезаписывать /etc/hosts
```

**Что делает скрипт:** если `NEW_HOSTNAME` пусто — ничего (имя остаётся как есть).
Иначе меняет имя, исправляет/добавляет строку `127.0.1.1` в `/etc/hosts` (с бэкапом)
и настраивает cloud-init, если он есть. Можно указать и полное имя (`web1.example.com`) —
тогда в `/etc/hosts` попадут оба варианта: `127.0.1.1 web1.example.com web1`.

Новое имя появится в приглашении после перелогина.

### 3.4. Swap

**Зачем.** Swap — место на диске, куда ядро выгружает редко используемую память, когда
RAM заканчивается. На дешёвом VPS с 1–2 ГБ памяти без swap при нехватке RAM срабатывает
**OOM killer** — ядро убивает самый «тяжёлый» процесс (часто базу данных или Docker-контейнер).
Со swap сервер вместо этого просто замедлится. Swap на диске в десятки раз медленнее RAM,
поэтому это страховка, а не замена памяти.

**Вручную:**

```bash
swapon --show                         # есть ли swap (пусто — нет)
fallocate -l 2G /swapfile             # создать файл 2 ГБ
chmod 600 /swapfile                   # читать может только root: там куски памяти процессов
mkswap /swapfile                      # разметить как swap
swapon /swapfile                      # подключить
echo '/swapfile none swap sw 0 0' >> /etc/fstab   # подключать при загрузке

# использовать swap только при реальной нехватке памяти
echo 'vm.swappiness = 10' > /etc/sysctl.d/99-swap.conf
sysctl -p /etc/sysctl.d/99-swap.conf
```

`vm.swappiness` (0–100, по умолчанию 60) — насколько охотно ядро выгружает память в swap.
Для сервера ставят 10: держать данные в RAM, а swap трогать только когда иначе никак.

**Что делает скрипт** (только при `ENABLE_SWAP=true`):

- если swap уже есть (некоторые хостинги создают его сами) — не создаёт второй;
- если на диске после создания осталось бы меньше 1 ГБ — предупреждает и не создаёт;
- создаёт `/swapfile` размером `SWAP_SIZE` через `fallocate` (мгновенно), а если файловая
  система его не поддерживает — через `dd` (медленнее, но работает везде);
- добавляет строку в `/etc/fstab` и `vm.swappiness = 10` в `/etc/sysctl.d/99-vps-init-swap.conf`.

Сколько ставить: при RAM до 2 ГБ — swap 1–2 ГБ; при 4 ГБ и больше обычно хватает 1–2 ГБ
«на всякий случай» или можно обойтись без него.

### 3.5. Автоматические обновления безопасности

**Зачем.** Уязвимости находят постоянно; сервер, который не обновлялся полгода, —
лёгкая цель. Пакет `unattended-upgrades` раз в день сам ставит **только обновления
безопасности** (из репозитория `-security`), обычные обновления не трогает.

**Вручную:**

```bash
apt install unattended-upgrades
dpkg-reconfigure -plow unattended-upgrades    # ответить «Yes» — создаст 20auto-upgrades
```

Настройки живут в двух файлах в `/etc/apt/apt.conf.d/`:

| Файл | Что в нём |
|---|---|
| `20auto-upgrades` | **включено ли**: обновлять списки и ставить обновления ежедневно (`"1"`) |
| `50unattended-upgrades` | **что именно** обновлять, перезагружаться ли автоматически (по умолчанию нет) |

**Что делает скрипт:**

- `ENABLE_AUTO_UPGRADES=true` — ставит пакет и записывает `20auto-upgrades`
  (ежедневно, раз в неделю чистит кэш скачанных пакетов). `50unattended-upgrades` не трогает —
  разумные настройки там уже из коробки;
- `ENABLE_AUTO_UPGRADES=false` (по умолчанию) — **ничего не трогает**. Выключать
  автообновления скрипт не будет: на Ubuntu они включены с завода, и это хорошо.
  На Debian их по умолчанию нет — там стоит поставить `true`.

### Проверка

```bash
timedatectl                    # Time zone: Europe/Moscow, System clock synchronized: yes
hostnamectl                    # Static hostname: web1
getent hosts $(hostname)       # 127.0.1.1 web1 — имя резолвится
swapon --show                  # /swapfile file 2G ...
cat /proc/sys/vm/swappiness    # 10
apt list --upgradable          # пусто — всё обновлено
systemctl status unattended-upgrades          # active, если автообновления включены
cat /var/log/unattended-upgrades/unattended-upgrades.log   # что они ставили
ls /var/run/reboot-required    # если файл есть — нужна перезагрузка
```

### Частые ошибки

- **`Could not get lock /var/lib/dpkg/lock-frontend`** — сразу после загрузки VPS apt занят
  автообновлением. Скрипт ждёт сам (до 5 минут); вручную — подождать или посмотреть,
  кто занял: `ps aux | grep -E 'apt|dpkg'`. Удалять lock-файлы руками нельзя — можно сломать dpkg.
- **Синее окно во время `apt upgrade`** («какой конфиг оставить?», «какие службы перезапустить?»)
  при ручном обновлении — безопасный ответ почти всегда «оставить текущую версию» (keep the local version).
- **Имя хоста вернулось после перезагрузки** — это cloud-init, см. 3.3.
- **`sudo: unable to resolve host ...`** — нет строки `127.0.1.1 <имя>` в `/etc/hosts`.
- **Swap не подключился после перезагрузки** — нет строки в `/etc/fstab` или опечатка в ней.
  Проверить без перезагрузки: `swapoff /swapfile && swapon -a && swapon --show`.
- **Сервер «завис» и тормозит** — память кончилась, система активно пишет в swap.
  Смотреть `htop` (полоска Swp) и искать, кто съел память; swap только отсрочил проблему.
